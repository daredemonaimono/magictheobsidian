# 対戦機能の核 設計書

作成: 2026-11-04 / 状態: ドラフト(じゅまの承認待ち)
対象: Magic the Obsidian(Obsidian プラグイン)の対戦機能のうち「核」だけ。

凡例: **【じゅま】** はじゅまが言ったこと。**【私の判断】** は Claude が置いた仮の判断(確認して直してよい)。

## 1. 目的と、なぜ今か

- 一人回しツールとは違い、**ゲーム性を感じる対戦**を作る。ゲーム性の中身は、**双方の行動に応答する必要があること**(優先権とスタック)。【じゅま】
- 0.40.0 までの対戦実装は、枠が決まる前に、動作が決まったものから順に実装したため、ツギハギになり、どのカードがどう処理されているか・正しく処理できているかを保守できなくなった。0.41.0 で白紙に戻し(0.40.0 は git タグ `archive/battle-rules-0.40.0`)、`ROADMAP.md` に「崩れない仕様を先に決める。決まるまで実装しない」と書いた。【じゅま】
- この設計書は、その「先に決める仕様」のうち、**核**(ノードによる能力の表現と、その土台)を決める。

## 2. 核とは何か

**カードを取り込み、能力にノード(部品)を割り当てる土台。** 【じゅま】

- 効果に対応する小さな汎用部品(ノード)を大量に用意し、n8n のように、パズルとして組み合わせて動作を作る。【じゅま】
- AI もノードを理解していて、カードテキストを読んでノードを組み立てられる(AI に頼める)。【じゅま】
- 人間も AI も同じノードを使う。AI が組んだものを人間が確認・修正できる。【私の判断】
- ルールの実装は「ノードの種類を増やしていくこと」になる。ルールは、盤面より先に実装する。【じゅま】

## 3. ゴール・ノンゴール・アンチゴール

**ゴール**
1. 能力を、4分類(呪文能力・起動型能力・誘発型能力・常在型能力)のどれかに必ず収められる。【じゅま】
2. カードごとの専用処理を持たない。すべて汎用ノードの組み合わせで表す。【じゅま】
3. どのカードが、どのノードで、実際に動くかを、いつでも確かめられる(保守できる)。【じゅま】
4. 全フォーマットに対応できる枠にする(実装は1対1から)。【じゅま】
5. ゲームの進行(ターン進行・優先権・スタックの解決)を、**テストで確かめられる範囲まで**核に含める。打ち消し3種が、スタックの上で応答し合うところまで動かす。【じゅま】
6. AI がカードテキストからノードを組み立てる機能を含める。組み立てた結果は **md に展開**し、人間が Obsidian 上で手で修正できるようにする(専用の編集画面は作らない。md が編集の場)。【じゅま】

**ノンゴール(この設計書の対象外)**
- 盤面の見た目(UI)と、UI の作り込み。ルールを先に作り、盤面はあとで載せる。【じゅま】
- ノードを編集する専用画面。md を直接編集することで代える。【じゅま】
- 多人数戦(統率戦の3人以上)の実装。1対1の実装のあと。【じゅま】
- 対戦相手 AI(ボット)の思考。この設計書は触れない。【私の判断】
- 0.40.0 のコードの再利用。白紙から作る。【じゅま】

**アンチゴール(動いても失敗とみなすもの)**
- **再利用できないノード**。パーツではなく、完成品のようなノードを作らないこと。【じゅま】
- 枠が決まる前に、動作が決まったものから順に足していくこと(0.40.0 の失敗)。【じゅま】

## 4. 決まっている方針

### 4.1 4分類
能力は次の4つに分ける。分類は MTG Wiki にきれいにまとまっていて、収めること自体は難しくない。【じゅま】

| 分類 | 起点 |
|---|---|
| 呪文能力 | 呪文を唱えること |
| 起動型能力 | コストの支払い |
| 誘発型能力 | きっかけ(イベント) |
| 常在型能力 | なし(継続効果・置換効果・軽減効果、スタックを使わない)【私の判断】 |

起点のノードの形は共通にして、種別を引数で渡す。【私の判断】

### 4.2 ノードの粒度
- それ以上分けられないパーツだけをコード(基本ノード)にする。完成品のようなノードは作らない。【じゅま】
- 既存のノードの組み合わせで言い表せる動作は、新しいノードにしない。繰り返し使う組み合わせは、コードではなくデータとして保存する定義(テンプレート)にする。【私の判断】
- ノードを足すときの審査は2つ。(a) ほかの動作に分けられないか。(b) ほかのカードでも使えるか。【私の判断】

### 4.3 カード個別の処理は作らない
- カード専用のノードは作らない。例: 「タップで3枚引く」は、起点のノードに「タップ」を設定し、「N枚引く」のノードに「3」を設定して表す。【じゅま】
- 打ち消しも、専用の「否認」ではなく、「打ち消す」ノードに、対象の条件(クリーチャーでない呪文、など)を引数で渡す。【私の判断】

### 4.4 タイミング
- インスタント・ソーサリーなどのタイミングは、カードタイプに従う。ノードにはしない。【じゅま】
- 能力ごとの例外(例: 装備は自分のメインフェーズで、スタックが空のときだけ)は、**「どうなったら」のノードに、トリガーの条件として設定する**。【じゅま】

### 4.5 つなぎの言葉
ノードをつなぐ言葉(いつ・どんな条件で・いつまで・何を指すか)は、動作のノードより先に、枠として決める。次の種類がある(実験の結果)。【私の判断】
- きっかけ(〜した時、〜するたび)と、その絞り込み(誰が・どのターンに)
- 条件(〜なら、〜かぎり)
- 持続(ターン終了時まで、〜している間)
- 結果の受け渡し(これにより、そうしたなら、それ、X、そのプレイヤー)
- 置換(代わりに、追加でもう一度)
- 繰り返し(各対戦相手につき、各クリーチャー)

### 4.6 保守(確かめられること)
- ノード1つにつき、MTG Wiki のルール解説の該当箇所に対応するテストを必ず付ける。【私の判断】
- ノードを直したときは、そのノードを使う全カードの処理を自動で再実行し、前回と同じ・変わった・壊れた、が分かるようにする。【私の判断】
- 各カードの状態を、完全に処理できる・一部の部品が未実装・処理を組めていない、の3つで出す。「動くはず」ではなく「実際に動いた記録」だけを見せる。【私の判断】
- ノードの定義を唯一の元データにする。AI への指示、検証、画面の一覧は、そこから作る。定義にない言葉は、機械的にはじく。【私の判断】

### 4.7 プレイヤーの持ち方
実装は1対1だけだが、プレイヤーを「2人固定」ではなく「リストと、相手という関係」で持つ。「各対戦相手につき」の繰り返しを最初から使う。【私の判断】

### 4.8 フォーマット
フォーマットごとの違い(デッキの枚数、初期ライフ、統率領域など)は、能力のノードとは別の、ゲーム設定の層に置く。【私の判断】

### 4.9 作り方(使うもの)
既存の仕組みに合わせる。TypeScript、esbuild、テストは `npm test`。データはノート(md)とプラグインのデータ。AI は Claude API(アプリ内)。【私の判断】

### 4.10 AI による組み立て(計画 2/2)
- API キーは **プラグイン設定に書き、Obsidian のキーチェーン(`app.secretStorage`)に保存する**。`data.json` にキーそのものを書かない(設定には、キーチェーン上の名前だけが残る)。【じゅま】
- **コマンドから AI にノードの組み立てを頼む**。コマンドを呼ぶと画面が開き、AI に書き換えてもらう**カードにチェックを入れる**。チェックしたカードだけを AI の処理の対象にする。**初期状態でチェックが入るのは、ノードの設定が無いカード**(`Rules/<カード名>.md` が無いカード)。カードのテキストを読んで、`Rules/<カード名>.md` を作る。【じゅま】
- 【私の判断】画面には `Cards/` の全カードを、状況(ok / partial / unbuilt / ルールなし)つきで並べ、名前で絞り込める。すでにルールがあるカードは未チェックで始まり、チェックして実行すると上書きになる。
- 【私の判断】上書きするときは、直前の内容を `Rules/_backup/<カード名>.md` に1世代だけ退避する(手で直した内容を失わないため)。
- 【私の判断】AI には、レジストリのノード一覧(id・日本語名・説明・引数)を指示文として渡す。一覧に無いノードは使わせない。表せない部分は、md の `## 未対応` に1行ずつ書かせ、状況レポートでは `partial` として出す。
- 【私の判断】AI の返事は、読み込み(`parseRule`)と検証(`checkCall`)を通ったものだけを保存する。通らなければ、エラーを渡して1回だけやり直させる。それでも通らなければ保存しない。
- 【私の判断】呼び出しは Obsidian の `requestUrl` で Messages API に直接送る(SDK は入れない)。理由: 本体は `isDesktopOnly: false` でモバイルでも動き、Obsidian の画面からの `fetch` は CORS で拒否されるため。
- 【私の判断】モデルは設定で選べる文字列で、既定は `claude-opus-5-5`。安く済ませたいときは `claude-sonnet-5-5` などに変えられる。

### 4.11 ルールの履歴
- カードの公式テキストや総合ルールが変わったときのために、ルールを AI に作り替えさせたとき・自分で組み直したときの**改変の歴史を、`Rules/_backup/` に md で残し、いつでも戻せるようにする**。【じゅま】
- 【私の判断】履歴は `Rules/_backup/<カード名>/<日時>-<種類>.md`(版ごとに1ファイル、書き換わる前の内容そのまま)。種類は `ai`(AI が作り替える前)・`edit`(手で直す前)・`restore`(版を戻す前)。内容が直前の版と同じなら残さない。
- 【私の判断】手で直したときは、連続した編集(5分以上あかない間)を1つの版にまとめる(保存のたびに版が増えないように)。その間の途中の状態は残らない。
- 【私の判断】コマンド「Battle: restore rule version」で、開いているルール(`Rules/<カード名>.md`、または履歴の md)の版の一覧を出し、選んだ版に戻す。戻す前の内容も履歴に入る。
- 【私の判断】以前の `Rules/_backup/<カード名>.md`(1世代だけの退避)は、そのまま残し、新しい履歴には取り込まない。

## 5. 進め方

範囲(確定): 核 = ノードの定義と実行、ゲームの進行(画面なしで、テストから動かせる形)、AI による組み立て、md への展開と、md からの読み込み。画面の作り込みは含まない。【じゅま】

1. **ノードを付ける実験**: 今のデッキ(Gentry Mono U、22種)のカードに、ノードを付ける。足りないノードを洗い出す。【じゅま】
2. 未実装のノードを、順に実装する。【じゅま】

実験の結果(文章上でやったもの)は付録 A。実装順の候補は、「応答し合う」核を最初に試すため、打ち消し3種(Negate、Essence Scatter、Spell Snare)から。【私の判断】

## 6. 未確認・ビルダーに任せるもの

**未確認**
- 「準備済(prepared)」の正しいルール(Emeritus of Ideation)。ルールの正本を見るまで、扱い方を決めない。
- 麻痺カウンター、チームワークの細かい動作(カードの文面だけを元にした)。
- 「枠」の具体的な形(ゲーム状態の持ち方、ノードの入力・出力の型、処理の順序の実行モデル)。これは、この設計書の方針の範囲内で、計画の段階でビルダーが詰める。

**ビルダー確認で決めたこと【私の判断】**
- 「実際に動いた記録」: ノードごとの単体テストの合格と、カード単位の最小シナリオの実行結果の、2つを根拠にする。カードのシナリオは、ノードの組み立てから機械的に作れる分は自動で作り、作れない分は Claude Code が書く。テストは AI(Claude Code)が書いてよい。じゅまは Obsidian で結果を見て確認する。
- 保存先: カードのノードの組み立ては、vault の `Rules/<カード名>.md` に置く(`Cards/` や `Decks/` と同じ並び)。プラグインのフォルダ内(`.obsidian/plugins/...`)は Obsidian の画面に出ないので、手で修正する用途に合わない(計画の段階で訂正)。vault の `Cards/` は Scryfall 由来のまま、触らない。書式はビルダーが決める。
- 枠の8項目(付録 A): 最初から、型と置き場所を決めて枠に入れる(後付けを避けるのが今回の趣旨)。実装するのは、最初のノード(打ち消し3種)に必要な分だけで、残りは拡張点として空けておく。
- 準備済・麻痺カウンター・チームワークは、最初の範囲に含めない。ルールの正本を確認する作業は、ビルダーがやってよい。
- 現状: 「白紙」にしたのは対戦関連(エンジン・Bot・ルールブック・カード処理)だけ。カード取り込み(Scryfall)、デッキ、コレクション、価格、ダッシュボード、MTG Wiki のリンクは残っている。ビルド・テストは `npm run build` / `npm test`。

**ビルダーに任せる**
- ノードの種類の具体的な一覧と命名。
- ノードの保存形式(md か JSON か、どこに置くか)。
- テストの仕組みと、再実行の仕組み。

## 付録 A: 実験の結果(デッキ22種)

分類の一覧:
- 呪文能力: Negate、Essence Scatter、Spell Snare(打ち消し + 対象の条件)/ Confusticate and Bebother、We Say Thee Nay!(支払わないかぎり打ち消す、選ぶ、代わりに)/ Amazing Acrobatics(選ぶ(両方可)、打ち消す、タップ)/ Aetherize、Into the Roil(キッカー)、Octopus Form(修整 + 呪禁、持続)、Accumulate Wisdom、Ancestral Recall
- 起動型能力: Island、Bender's Waterskin(マナ能力)/ Cryogen Relic(コスト + 麻痺カウンター)/ Chandra、Jace(忠誠度能力)/ 装備(Light Jammer、Wizard's Staff)
- 誘発型能力: Brineborn Cutthroat、果敢(Elementalist Adept、Wizard's Staff)、Cryogen Relic、Jace、Light Jammer、Emeritus、Chandra の紋章
- 常在型能力: Flash、飛行、護法、Geist of Saint Thalia(コスト軽減)、Light Jammer(+1/+2)、Wizard's Staff、Waterskin(アンタップ)、Witness Protection(全能力を失う、色・種別・名前・基本P/T)

枠として先に決める必要があると分かったもの:
1. 結果の受け渡し(これにより、そうしたなら、それ、X)
2. 置換効果(代わりに、追加でもう一度、麻痺カウンター、Waterskin)
3. 継続効果の重ね合わせ(Witness Protection など。ルールのレイヤー)
4. 呪文を唱えたときの記録(キッカー、チームワーク、選んだモード)
5. 持続の長さと、オブジェクトの状態(攻撃中、タップ中、準備済)
6. 新しい物を作るノード(トークン、紋章)
7. 「各対戦相手につき」の繰り返し
8. マナの使い道の制限

難しさの目安: 枠にきれいに収まる約10枚 / 中くらい約8枚 / 難しい約5枚(Chandra、Jace、Wizard's Staff、Witness Protection、Emeritus)。
