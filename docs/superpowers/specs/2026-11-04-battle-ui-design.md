# 対戦の画面の設計

日付: 2026-11-04 / 作者: じゅま(以下、ユーザー)と AI の相談 / 状態: 承認待ち

## 1. 何を作るか、なぜか

Magic the Obsidian に、**AI と対戦できる画面**を作る。いまは、カードの能力をノードで組んで動かす「エンジン」(`src/battle/`)が、画面なしで完成している(ターンの進行・優先権・スタック・マナ・戦闘・状況起因処理・準備済・護法まで。テストで確かめてある)。この**エンジンを、画面から遊べるようにする**のが、この設計書の仕事。

ユーザーが目指すもの: よくある「一人回しツール」ではなく、ゲームとして遊べる対戦。見た目は、**マジック 2015(Duels of the Planeswalkers 系)の UI**: 斜め見下ろしの盤面、手前に大きな手札、ダメージの処理では拡大カードが前に出る。「臨場感が強い」ことが大事。

成功したとき: デッキ「Gentry Mono U」のように、ルールを設定したデッキで、AI を相手に1試合を最後まで遊べて、勝ち負けが付く。エンジンの状態と画面が食い違わない(画面は、エンジンの状態を描くだけ)。

## 2. 目標・非目標・やってはいけないこと

**目標**
- 斜め見下ろしの盤面で、1対1の対戦を遊べる(土地、マナ、呪文、攻撃、ブロック、勝敗)。
- 相手は2種類: ①**雑魚 CPU**(できる処理だけを、機械的に処理する。API なし)、②**Claude の AI**(API で判断。選択肢が1つの場面は機械的に処理)。
- 小さく区切って、軽い処理から順に**リリース**し、そのたびにユーザーが確認する(8段階。7節)。

**非目標(いまはやらない)**
- 多人数戦(2人戦だけ)。先手後手の決め方(最初は、自分が先手)。マリガンは、**段階4で作る**(下の7節の4)。段階2・3の間は、手札7枚で始まる(マリガン無し)。
- 追加ターン、ターンの飛ばし。
- 履歴の保存とリプレイ(最後の段階。ユーザーが「後でいい」と言った)。
- ネットワーク対戦、スマホ向けの操作。
- 統率戦(Commander)のデッキでの対戦(ライフ 40・統率者ダメージが無いため。9節の6)。

**やってはいけないこと(失敗とみなす)**
- **既存の動きを壊す。** デッキ・コレクション・カード一覧・ノード設定画面・AI のルール構築は、そのまま動くこと。エンジンのテスト(`npm test`)は、常に全部通すこと。
- 画面が、エンジンとは別にルールを持つこと(例: 画面側で「土地は1ターン1枚」を数える)。ルールは、エンジンだけが持つ。
- ルールの例外を作ること(例: 基本土地だけ、ルールが無くてもマナが出る)。**ルールが設定されていないカードは、すべて同じ扱い**(下の「決めたこと」)。
- カクつく・重い画面。

## 3. 制約

- Obsidian のプラグイン(Electron)。タブの中の画面(`ItemView`)として作る。BRAT で配る。専用のゲームエンジンや重い描画ライブラリは入れない。依存の追加は最小に。
- 既存のコード: 画面は `src/*View.ts`、エンジンは `src/battle/`。エンジンの入口は `castSpell` / `castPrepared` / `activateAbility` / `playLand` / `declareAttackers` / `declareBlockers` / `passPriority` / `startGame`。状態は `Game`(`src/battle/state.ts`)。ターンを公式どおりに進めるには `Game.strictTurns = true`、カード自体のマナコストを払うには `Game.payManaCosts = true`(画面の側で真にする)。
- 画面クラスのメンバー名は、Obsidian 本体の `open` `close` `load` などと重ねない(画面が空白になる。`test/viewnames.test.ts` が確かめる)。
- ファイルの書き込みは、plugin 側のコードだけ。`Cards/` `Decks/` `Rules/` の中身は、勝手に書き換えない(いまの画面と同じ扱い)。
- 重さ: ホバーの前面表示は CSS の `transform` だけで行う。盤面の更新は、変わったカードだけを描き直す(全部を作り直さない)。画像は遅延読み込み(ノートに保存済みの URL を使う)。アニメーションは `transform` と `opacity` だけ。実際の重さは、カードが多い盤面で確かめる。

## 4. ユーザーが決めたこと

**見た目**(モックは `docs/superpowers/specs/2026-11-04-battle-ui-mockups/`。参考: マジック 2015 の画面)
- 斜め見下ろしの盤面。奥が相手、手前が自分。自分の手札は、手前に大きく、こちら向き。**相手の手札は、盤面に出さない**(相手の手札に干渉する効果のカードを使ったときだけ、目の前に手札が現れる演出。段階6以降)。視点は、マジック 2015 の画面のように、少し上から(傾きは 24 度)。山札と墓地は、**山札の絵(裏向き)と、枚数に応じた厚み**で見せる(墓地は一番上のカードを見せる)。
- 左下に自分のアバターとライフ、右上に相手。山札と墓地は脇に置く。赤い帯が「戦闘」のライン。攻撃しているクリーチャーは紫に光る。
- フェイズ表示は、公式の5フェイズ(開始・戦闘前メイン・戦闘・戦闘後メイン・最終)に合わせる。ステップは、そのフェイズの中に小さく出す。
- 右のサイドバー: **上**=カーソルを合わせたカードの画像と効果テキスト、**下**=対戦のログ(例: 「あなたが島をタップして {U} を出した」)。
- 手札にカーソルを合わせると、重なっているカードが前面に出る。
- 戦闘ダメージでは、関わるカードが前に拡大して出て、ダメージの数字が出る。先制攻撃・二段攻撃は、2回。**この演出は、設定でオフにできる**。
- ダメージを受けたカードの上に、ダメージ数を出す。
- マナ・プールは、自分のアバターの近くに色ごとに出す(私の案。ユーザーは、マナを「保持している状態」としか言っていない)。

**操作**
- 土地をクリックでタップ → マナがプールに保持される → カードを使うと、プールから払う(手動)。
- **ダブルクリック**でカードを使う(手札: 唱える・土地を出す。土地・マナ能力のあるカード: タップしてマナを出す)。1回のクリックは、選択とプレビュー用。
- 複数の能力があるカード(プレインズウォーカーなど): **1回クリックで能力の一覧が出る。ダブルクリックなら、一番上の能力**。
- 途中でやめるのは **Esc** だけ(右クリックは、Obsidian のメニューと重なるので使わない)。
- **攻撃**: 攻撃クリーチャー指定のとき、「攻撃しない(スキップ)」ボタンが出る。攻撃するクリーチャーをクリックで選び、「確定」ボタン。召喚酔い・タップ済みは、選べない(薄く表示)。**ブロック**も同じ形(ブロッカーをクリック → ブロック先をクリック → 「確定」)。
- **複数の対象**: 対象をクリックで選び、「2 / 2」のように数を出す。数が足りたら「確定」。
- 優先権の止まり方は、**設定で選べる**: 「毎回止まる」/「使えるものがあるときだけ止まる(無ければ自動でパス)」。
- **ルールが設定されていないカード**を使ったとき: ログに「ルールが設定されていません。スキップします。」と出して、効果は飛ばし、ゲームは進める。**基本土地も、ルールが無ければマナを出せない**(例外を作らない)。

**対戦の始め方**
1. 自分のデッキを選ぶ。
2. そのフォーマットで使える相手のデッキを、一覧から選ぶか、ランダムで決める(相手のデッキは、vault の `Decks/` から)。
3. 相手の種類(雑魚 CPU / Claude の AI)を選ぶ(私の案)。
4. `startGame` で手札を7枚ずつ引いて、始める。

## 5. 私が決めたこと(ユーザーには確かめていない。直してよい)

- 盤面は、**HTML と CSS の立体表示(`perspective` + `rotateX`)**で作る。canvas や WebGL は使わない。
- 画面は、エンジンの状態(`Game`)を描くだけ。操作は、エンジンの入口を呼ぶ。エンジンの状態が変わったら、差分だけを描き直す。
- 相手は、2種類とも、同じ入口(「いまできる行動の一覧から1つ選ぶ」)につなぐ。あとから種類を増やしたり、切り替えたりできる。
- 画面を開くコマンド、設定項目(演出のオン・オフ、優先権の止まり方、相手の種類)は、既存の設定画面(`src/settings.ts`)に足す。

## 6. 既知の難所(ビルダーが、計画の前に知っておくこと)

- **カード → `GameCard` の変換**: ゲームの `GameCard` は、`name`(ルールのノートの名前と同じ)・`typeLine`・`mv`・`manaCost`・`power` / `toughness`(数)・`keywords`・`colors`・`loyalty`・`token` を持つ。いまの `Cards/` のノート(frontmatter)には、`name` `type_line` `mana_cost` `cmc` `power` `toughness` `keywords` `colors` はあるが、**`loyalty`(忠誠度)が保存されていない**。`power` が `*` のカードもある。ルールのノートの名前は、カードのノートのファイル名(両面カードは `A - B`)で、frontmatter の `name`(`A // B`)とは違う。変換の決まりは、段階2で決める。
- **判断の入力(`Decider`)が同期**: エンジンは、捨てるカード・ライブラリーの上から選ぶカード・誘発型能力の対象・「してもよい」・「支払わないかぎり」を、同期の関数(`Game.decide`)で受け取る。人間の入力は、待てない。段階4(スタックと対象)で、「エンジンが一時停止して、画面の入力を待つ」形にする必要がある。方法(`Decider` を非同期にする / エンジンが「保留中の選択」を持つ)は、段階4で決める。それまでの段階(1〜3)は、既定の動きで足りる。
- **画面のテスト**: DOM を持つテストの仕組みは、いまのリポジトリに無い。画面の見た目は、ユーザーが確認する。ロジック(エンジンの状態 → 画面に出す内容への変換、操作 → エンジンの入口の呼び出し)は、画面から切り離して、`npm test` で確かめる。

## 7. 段階(軽いものから、1段ごとにリリースして確認する)

1. **盤面を見るだけ**: 斜め見下ろしの盤面、手前の手札(ホバーで前面)、アバターとライフ、サイドバー(上: カード、下: ログ)。サンプルの局面を表示するだけで、操作はまだ無い。確認: 見た目と、重さ。
2. **対戦を始める**: デッキの選択、相手のデッキの選択(フォーマットで絞る / ランダム)、`startGame`、手札の表示。カード → `GameCard` の変換。ルールが無いカードの扱い(ログ)。確認: デッキが読み込まれて、手札が配られる。
3. **自分のターンの操作**: 土地のタップ、マナ・プール、ダブルクリックでカードを使う、能力の選択、フェイズ表示と「次へ」ボタン、ログ。対象を取らないカードだけ。
4. **スタックと対象**: スタックの表示、対象の選択、優先権の設定、`Decider` の入力待ち。**マリガン**もここで入れる(ロンドン・マリガン: 手札を見て、キープかマリガンを選ぶ。マリガンなら、手札を山札に戻して切り、7枚引き直し、引き直した回数だけ、底に置くカードを選ぶ。相手の CPU は、常にキープ)。入力待ちの仕組みを使う。
5. **雑魚 CPU**: 相手が、できる処理を機械的に処理して動く。1試合を通して遊べる。**マリガンもする**(ユーザー依頼 2026-11-05。単純な決まりで: 手札の土地が何枚以上あり、かつ、コストの低いカードがあればキープ、そうでなければマリガン。枚数の基準は設定できるようにする。段階4cまでは、相手は常にキープ)。
6. **戦闘**: 攻撃・ブロックの選択と確定、ダメージ数、拡大カードの演出(オフにできる設定)。
7. **Claude の AI の相手**(実装済み 0.79.0): 盤面とできる行動の一覧(番号つきの選択肢)を、既存の API の仕組み(`src/battle/claude.ts`)で渡す。選択肢が1つの場面は機械的に処理。応答も含めて全部 Claude(ユーザー指定 2026-11-05)。モデルは設定で切り替え。API が失敗したら、以降は雑魚 CPU。
8. **履歴の保存とリプレイ**: AI との対戦の履歴(エンジンの入口の呼び出しの並び)を保存して、再生する。**あとで(ユーザーの構想 2026-11-05)**: AI 自身が、リプレイから学習して、デッキごとのマークダウン(「AI ルール」: そのデッキの動かし方・コンボ・マリガンの基準など)を作る。AI は、対戦のたびにそれを読み、確認し、書き直して、自己調整する。置き場所はデッキごとのノート(AI 領域。vault の `Decks/` などは勝手に書き換えない: 置き場所は、そのときに決める)。

各段階の完了 = そのテスト(エンジンの状態 → 画面の内容の変換など)が通り、ユーザーが画面で確認して、リリースする。

## 8. ビルダーに任せること

- 画面クラスの分け方・ファイル名・CSS の細かい値・アニメーションの細部。
- 相手の「雑魚 CPU」の細かい方針(機械的に処理する、という範囲で)。
- 設定項目の置き場所と名前。

## 9. 計画の前に、決めておくこと(ビルダーの確認で出た点への答え)

「ユーザー」= ユーザーが決めた / 「私」= 私が決めた(直してよい)。

1. **基本土地などのルール**(ユーザーが決めた): 例外は作らない。ルールが無いカードは、使うと「ルールが設定されていません。スキップします。」。ユーザーの vault には、基本土地(Island など)のルールが、すでにある。**私が足すこと**: 段階2で、対戦を始める前に「ルールが設定されていないカード」の一覧を見せる(始めるのは、そのまま始められる)。テストは、手で作ったルール(ノードの組み)で書く。vault のノートには依存しない。
2. **エンジンを変えてよいか**(私): 変えてよい。`npm test` が全部通ること。既存のテストを書き換えてよいのは、その前提が正しく変わったときだけ(理由を書く)。**判断の入力の入力待ち**(段階4)は、エンジンが「保留中の選択」を持つ形(`Game` に、いま必要な選択を表す状態を持たせ、画面・CPU・AI が、同じ入口で答える)を第一候補にする。最終的な形は、段階4の最初に、小さな試作で決める。
3. **「いまできる行動の一覧」**(私): エンジンの側に作る(`src/battle/actions.ts` など。テストつき)。優先権の自動パスの設定、雑魚 CPU(段階5)、Claude の AI(段階7)が、同じ一覧を使う。一覧には、唱えられるカード、起動できる能力、出せる土地、攻撃できるクリーチャー、ブロックできるクリーチャー、対象の候補を含める。「ルールが無いカードはスキップ」は、エンジンの側の処理にする(画面は、ログを出すだけ)。
4. **相手がまだ動けない間**(段階3〜4。私): 相手は、すべての優先権を自動でパスして、何もしない(攻撃もしない)。自分のターンの操作の確認に集中できる。
5. **忠誠度と `*` のパワー**(私): `loyalty` は、`toMarkdown`(カードのノートを作る処理)で frontmatter に保存して、「情報取得」(ユーザーが押す、いまと同じ取り直し)で付く。画面が `Cards/` を勝手に書き換えることはしない。パワーが `*` のカードは、パワー・タフネスを 0 として扱う(エンジンに、特性定義能力が無いため。限界として記録する)。
6. **フォーマット**(私): 自分のデッキのフォーマットは、デッキのノートに保存されているもの(デッキ画面のヘッダーで選ぶもの)。相手のデッキは、そのフォーマットで使えるもの(`src/rules.ts` の判定を使う)。**統率戦(Commander)のデッキは、対戦に使えない**(ライフ 40・統率者ダメージが無いため。非目標に追加)。ライフは 20 固定。
7. **段階1のサンプルの局面**(私): 手で書いた固定のデータではなく、`createGame` で作った、本物の `Game`(`src/battle/samples.ts` と同じ作り方)を、画面に描く。攻撃クリーチャーの紫の光・赤い帯も、その `Game` の状態(`attacking` と `combatPhase`)から出す。
